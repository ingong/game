# 에셋 점검 — 2026-09-07

> 이 문서는 관리 시스템 도입 직후의 점검 기록이다. 이후 같은 날 실제 아트 스타일을
> 수정해 투명도와 현재 아틀라스 변환 재현성을 개선했다. 최신 에셋·크기·검증 결과는
> [스타일 변경 기록](prismatic-assets.md)을 참조한다.

현재 프로젝트의 에셋 파일, 출처 기록, 실제 렌더링 코드와 제출 빌드를 확인했다.
새 관리 체계는 개발용으로 추가했으며, 기존 PNG의 픽셀과 게임 동작은 유지했다.

## 현황

| 분류 | 등록 수 | 파일 크기 | 사용 방식 |
| --- | ---: | ---: | --- |
| 실행용 PNG | 1 | 2,402 B | HTML 안에 데이터 URI로 포함 |
| 실행용 코드 에셋 | 3 | 개별 코드 크기는 카탈로그 참조 | 캐릭터 대체 렌더링·효과, 환경·HUD, 스테이지 |
| 콘셉트 PNG | 3 | 4,024,161 B | 개발용 원본·디자인 참고 |
| 외부 참고 및 출처 문서 | 11 | 1,131,948 B | PNG 7개, ZIP 2개, 문서 2개 |
| 합계 | 18 | 물리 에셋 파일 5,158,511 B | 코드 파일 크기는 합계에서 제외 |

물리 에셋 15개를 전부 등록했다. PNG 11개는 CRC와 디코딩 검사를 통과했으며,
현재 파일 전체를 기준으로 SHA-256이 같은 중복 파일은 없었다. ZIP 내부 파일과
압축을 풀어 둔 참고 파일의 중복은 별도 집계하지 않았다. 오디오와 번들 폰트는
현재 없으며 HUD는 시스템 고정폭 글꼴을 사용한다.

제출 ZIP은 도입 전후 모두 **12,767 / 13,312 B**다. 남은 용량은 **545 B**다.
개발용 콘셉트와 참고 파일 약 4.92 MiB는 제출물에 포함되지 않는다.

## 이번에 개선한 관리 문제

- **실행용 원본과 콘셉트 혼재:** 작은 아틀라스를 `assets/runtime/`으로 이동했다.
- **Base64 수동 동기화:** 원본 PNG와 프레임 메타데이터에서 생성 모듈을 만들도록
  바꿨다. 테스트와 빌드가 생성 파일의 누락·불일치를 검사한다.
- **에셋 단위 정보 부족:** ID, 용도, 크기, 출처 기록, 이용 조건, 원본 관계를
  `assets/manifest.json`에 모았다. 증거가 없는 제작자·도구는 미상으로 표시했다.
- **전체 점검 경로 부재:** 누락·미등록·중복, PNG 손상, 프레임 규격과 용량을
  점검하는 CLI와 이미지·동작을 확인하는 로컬 카탈로그를 추가했다.
- **README와 실제 빌드 불일치:** “이미지가 없다”는 설명을 “내장 PNG 아틀라스와
  Canvas 코드 사용”으로 바로잡았다.
- **실제 스프라이트 경로의 테스트 공백:** 기존 Node 테스트는 대체로 `Image`가
  없는 기하 도형 대체 경로를 확인했다. 로딩된 아틀라스의 프레임 선택·크롭과
  이미지 디코딩 실패 시 대체 경로를 확인하는 테스트를 추가했다.

## 개선 우선순위

### 1. 아틀라스 투명도와 가장자리 — 높음

`assets/runtime/unicorn-chibi-atlas.png`는 160 × 56, 24색 인덱스 PNG다.
**8,960픽셀 전부 반투명**이며 알파 범위는 **1–253**이다. 알파 0인 배경 픽셀과
알파 255인 불투명 픽셀이 하나도 없다. 배경에 따라 미세한 사각형 흔적이나 색
혼합이 생길 가능성이 있다. 결함의 실제 가시성은 게임 스케일과 배경에 따라 다르다.

흰색·어두운색·붉은 배경에서 캐릭터 가장자리를 비교한 뒤, 배경과 실루엣 경계를
구분해 알파를 정리하는 작업을 권장한다. 모든 알파를 일괄 임계 처리하면 가는
뿔·갈기·발 윤곽이 손상될 수 있다. 이 점검에서는 원본을 변경하지 않았다.

### 2. 아틀라스 제작 과정의 재현성 — 높음

1983 × 793 원본 시트에서 160 × 56 아틀라스를 만든 크롭 좌표, 축소 방식,
팔레트 양자화 설정, 프레임 기준점이 저장되어 있지 않다. 이번에 재현 가능해진
범위는 **현재 PNG → 코드 임베딩**이다.

다음 아트 수정 때 편집 원본과 변환 스크립트를 함께 보관하고, 32 × 56 프레임마다
발 접지점·크롭 영역을 명시하는 것이 좋다. 개별 제작자와 생성/편집 도구 기록도
보완해야 한다. 현재 README의 원본 작업 분류만으로 그 세부 이력을 증명할 수 없다.

### 3. 외부 참고 원본의 배포 범위 확인 — 높음

`assets/references/itch/SOURCES.md`에는 muscle-runner 원본 팩의 재배포 제한이
기록되어 있으며 `muscle-runner-reference.png`가 저장소에 포함되어 있다. 게임
제출물에서는 제외되지만 저장소 배포 범위는 별도로 확인할 필요가 있다.

이는 **로컬에 저장된 조건과 파일 위치를 대조한 점검 항목**이다. 최신 원문을
재확인하거나 이용 조건에 대한 법적 판단을 내린 것은 아니다. 배포 전 원본 조건과
실제 공개 범위를 확인하고, 필요하면 출처 링크만 남기는 방식을 검토한다.

### 4. 점프·착지·충돌 동작 구분 — 중간

`runnerFrame()`은 일반 점프와 이단 점프에 프레임 3을 공통으로 사용하고, 착지와
충돌에는 프레임 4를 공통으로 사용한다. 기하 도형 대체 경로에는 더 많은 포즈가
있지만, 정상 로딩 상태의 PNG 스프라이트에는 그대로 적용되지 않는다. 현재도
회전·위치·스케일 변형으로 일부 상태 차이는 표현한다.

남은 ZIP 여유가 545 B이므로 새 시트를 크게 늘리기 전에 기존 프레임의 타이밍과
회전·압축 변형으로 상태 구분을 강화하는 안을 우선 비교한다. 새 프레임이 필요하면
프레임 순서·좌우 반전·접지점을 함께 검증해야 한다.

### 5. 대체 렌더러와 색상 관리 — 중간

`src/art.mjs`에는 PNG 외에 캐릭터 기하 도형 대체 렌더러가 남아 있다. 이미지
로딩 전과 실패 시 도움이 되지만, 정상 스프라이트와 따로 관리해야 하는 비용이
있다. 제거할 경우의 ZIP 절감량은 이번에 별도로 측정하지 않았다.

불러오기 실패 정책을 먼저 정한 뒤 단순화 여부를 비교한다. 배경 팔레트는
`src/render.mjs`, 대체 캐릭터 팔레트는 `src/art.mjs`, 실제 캐릭터 팔레트는 PNG에
있다. 실제 화면의 명도·윤곽 대비를 기준으로 함께 검토할 팔레트 표를 추가하면
이후 아트 수정 시 일관성을 유지하기 쉽다.

### 6. 개발용 원본 저장 비용 — 낮음

콘셉트 원본만 약 3.84 MiB이며 참고 ZIP과 추출 파일도 함께 보관 중이다. 현재
규모에서 별도 외부 관리 서비스나 Git LFS를 도입할 필요성은 크지 않다. 버전별
원본이 늘어날 때 보관 정책을 정하면 된다. 이 파일들을 압축하거나 삭제해도
현재 게임 ZIP은 줄어들지 않는다.

### 7. 캐릭터와 환경의 디테일 밀도 — 중간

실제 제출 빌드의 시작 화면에서는 픽셀 단위로 묘사한 캐릭터에 비해 도로·용암의
넓은 단색 면과 반복 구조가 두드러진다. `red-stage-concept.png`에 있는 촘촘한
벽돌·균열·깊이 표현과 차이가 있다. JS13K 제약에서 의도한 단순화일 수 있으므로
콘셉트와 같은 밀도를 그대로 목표로 삼을 필요는 없다.

추가 PNG를 넣기 전에 기존 절차적 패턴을 활용해 가까운 도로의 균열·경계와
먼 배경의 명도 차이를 조정하는 편이 적합하다. 장애물의 경고 무늬가 배경 장식과
경쟁하지 않는지 실제 플레이 크기에서 함께 비교하는 것을 권장한다.

## 점검 방법과 범위

`npm run assets:check`, `npm test`, `npm run build`, `npm run assets:catalog`를
사용했다. 로컬 브라우저에서 카탈로그 이미지, 검색·분류·빈 결과, 프레임·배경
전환을 확인했다. 프레임 크롭과 대체 렌더링은 자동 테스트로 함께 검증했다.
제출 HTML을 브라우저에서 열어 시작 화면의 스프라이트와 환경이 표시되는 것과
해당 확인 중 경고·오류 로그가 없는 것을 확인했다.
외부 라이선스 원문의 최신성, AI 생성 여부, 원본 제작자, ZIP 안의 모든 파일을
별도로 증명한 점검은 아니다.

카탈로그 실행과 새 에셋 등록 절차는 [관리 가이드](asset-management.md)에 있다.
